NVIDIA released [ASPIRE](https://github.com/NVlabs/ASPIRE) v1.0 in October: coding agents write robot programs, and it reports 99% success on 80 LIBERO-Pro tasks.

I wanted to know if it was a one-off. It isn't. I counted 26 projects outside NVIDIA in the same space, most since September. A frozen LLM writes robot code, runs it, fixes it and keeps what works. The field calls it agentic robotics, and CoRL 2026 gave it a [workshop](https://agentic-robotics-workshop.github.io).

So I set ASPIRE up on Anyscale.

![A robot arm in a LIBERO scene picks up a blue soup can and puts it in a basket](/blog_images/aspire-episode-on-anyscale.gif)

_ASPIRE's example program on one L4 on Anyscale. Success in 27 s._

## Training is fixing code

ASPIRE trains no weights. Its README says "training" is skill refinement instead of gradient descent.

An agent writes a program and debugs it in sim on 15 seeds. Then the program is scored on 50 new seeds. Fixes a second agent can reproduce become skills for the next task.

![ASPIRE's loop: an agent writes a program, the sim runs it on 15 seeds and the agent fixes it from the logs, the program is scored on 50 new seeds, and verified fixes become skills the next task starts with](/blog_images/aspire-loop.png)

## Two halves: the robot and the models

The program never touches a simulator or a model directly.

**One environment interface,** with LIBERO, Robosuite, BEHAVIOR-1K or two real YAM arms behind it.

**Three model services,** each with its own port and Python environment:

- SAM3 finds objects from a text prompt. GPU.
- PyRoki solves inverse kinematics. CPU.
- cuRobo plans collision-free paths. GPU.

![A robot program, cut down from ASPIRE's examples: localize_object calls SAM3, and move_to_pose calls PyRoki and cuRobo](/blog_images/aspire-robot-program-code.png)

Every sim shares one copy of each, "rather than one model loaded per simulator process" ([their code](https://github.com/NVlabs/ASPIRE/blob/fa00f0ef2bc1d91d594b9aa502c22133c9f538f7/src/cap_harness/providers/service_runtime.py#L3-L6)).

## I pitched the same split for driving sims

On 21 Oct I spoke at Encord's Long Horizon: "Why Sim Platform Shouldn't Be a Batch Job."

{/* TODO: link the talk post (calendar #17) here once it is up. */}

A common setup gives each driving scenario its own batch job, with its own copy of the model. The model works 15 ms of each 1 s tick. Its GPU sits 98% idle.

![A closed-loop batch job: each AWS Batch job holds a sim and its own copy of the driving model, and the model GPUs show 1.5% busy](/blog_images/aspire-closed-loop-one-model-per-sim.gif)

My fix: sims in one pool, models in another, every sim calling them.

![Two pools on one cluster: sims as Ray actors on RTX GPUs, the policy on Ray Serve on H100s](/blog_images/aspire-two-pools.png)

Same split. Arms instead of cars.

## Ray runs both halves on a cluster

ASPIRE runs its services by hand, on one machine.

- **Placement:** a GPU index per service. Ray places copies on any node, on part of a GPU.
- **Copies:** one per service. Serve adds copies as calls queue.
- **Failures:** a bash supervisor stops all three when one dies, and restarts none. Serve replaces the copy that died.
- **Sims:** a process pool on one box. Ray tasks spread across nodes.
- **Hardware:** the multi-GPU profile needs a 4-GPU box, and AWS had none for me on demand. 1-GPU nodes came up in minutes.

![The same two halves on Ray: episodes as Ray tasks spread across GPU nodes, and SAM3, PyRoki and cuRobo as Serve deployments, each with its own number of copies](/blog_images/aspire-on-ray.png)

![ASPIRE's three services as Serve deployments with num_replicas set to auto, two on half a GPU and PyRoki on two CPUs, and each episode as a Ray task on a quarter GPU](/blog_images/aspire-on-ray-code.png)

Triton and Knative cover parts of this. Ray's edge is one program and one autoscaler for CPU and GPU nodes.

I work at Anyscale, which builds Ray. I haven't ported ASPIRE yet.

## What I'll measure next

ASPIRE logs each service's calls and seconds per episode. Time between calls, divided by time per call, is how many sims one copy can feed. That sets the copy counts.
