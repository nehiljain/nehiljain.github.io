NVIDIA released [ASPIRE](https://github.com/NVlabs/ASPIRE) v1.0 in October: coding agents write robot programs, with 99% success on 80 LIBERO-Pro tasks.

I wanted to know if it was a one-off. It isn't. I counted 26 projects outside NVIDIA in the same space. A frozen LLM writes robot code, runs it, fixes it and keeps what works. It's called agentic robotics, and CoRL 2026 gave it a [workshop](https://agentic-robotics-workshop.github.io).

So I set ASPIRE up on Anyscale.

![A robot arm in a LIBERO scene picks up a blue soup can and puts it in a basket](/blog_images/aspire-episode-on-anyscale.gif)

_ASPIRE's example program on one L4, success in 27 s._

## Training is fixing code

ASPIRE trains no weights. Its README says "training" is skill refinement instead of gradient descent.

An agent writes a program and debugs it in sim on 15 seeds. The program then faces 50 new seeds. Fixes a second agent can reproduce become skills for the next task.

![ASPIRE's loop: an agent writes a program, the sim runs it on 15 seeds and the agent fixes it from the logs, the program is scored on 50 new seeds, and verified fixes become skills the next task starts with](/blog_images/aspire-loop.png)

## Two halves: the robot and its services

The program never touches a simulator or a service directly.

**One environment interface,** with LIBERO, Robosuite, BEHAVIOR-1K or two real YAM arms behind it.

**Three perception and planning services,** each with its own port and dependencies:

- SAM3 finds objects from a text prompt. GPU.
- PyRoki solves inverse kinematics. CPU.
- cuRobo plans collision-free paths. GPU.

![A robot program, cut down from ASPIRE's examples: localize_object calls SAM3, and move_to_pose calls PyRoki and cuRobo](/blog_images/aspire-robot-program-code.png)

Every sim shares one copy of each, "rather than one model loaded per simulator process" ([their code](https://github.com/NVlabs/ASPIRE/blob/fa00f0ef2bc1d91d594b9aa502c22133c9f538f7/src/cap_harness/providers/service_runtime.py#L3-L6)).

## I pitched the same split for driving sims

On 21 Oct I spoke at Encord's Long Horizon: "Why Sim Platform Shouldn't Be a Batch Job."

A common setup gives each driving scenario its own batch job and model copy. The model works 15 ms of each 1 s tick. Its GPU sits 98% idle.

![A closed-loop batch job: each AWS Batch job holds a sim and its own copy of the driving model, and the model GPUs show 1.5% busy](/blog_images/aspire-closed-loop-one-model-per-sim.gif)

My fix: sims in one pool, models in another.

![Two pools on one cluster: sims as Ray actors on RTX GPUs, the policy on Ray Serve on H100s](/blog_images/aspire-two-pools.png)

Same split. Arms instead of cars.

## What Ray Serve adds

ASPIRE runs its services by hand on one machine.

![The same two halves on Ray: episodes as Ray tasks spread across GPU nodes, and SAM3, PyRoki and cuRobo as Serve deployments, each with its own number of copies](/blog_images/aspire-on-ray.png)

**More out of each GPU**

- **Batching:** GPU services take one call at a time. `@serve.batch` runs the queue as one pass. cuRobo 0.8 plans in batches.
- **Fractional GPUs:** SAM3 and cuRobo used 3.8 GB of my L4's 24 GB. Serve packs them beside the sims.
- **Multiplexing:** cuRobo hand-rolls a per-robot planner cache. `@serve.multiplexed` caps it and routes calls to the right copy.

![Three panels: batching, four sims' calls run as one GPU pass on SAM3. Fractional GPUs, one L4 split between two sims, SAM3 and cuRobo. Multiplexing, calls for each robot routed to the cuRobo copy that holds its planner](/blog_images/aspire-serve-gpu.png)

**Less to run by hand**

- **Composition:** `move_to_pose` calls PyRoki, then cuRobo. In one Serve app that's one call, and each step scales alone.
- **Compaction:** copies follow the calls, to zero between runs. Anyscale's replica compaction packs the rest onto fewer nodes.
- **Restarts:** Serve replaces a dead copy. ASPIRE's supervisor stops all three.

![Three panels: composition, a sim makes one call to a planner that calls PyRoki and cuRobo inside one Serve app. Compaction, copies left on two nodes move onto one and the empty node shuts down. Restarts, a dead SAM3 copy is replaced while the others keep serving](/blog_images/aspire-serve-ops.png)

![ASPIRE's three services as Serve deployments with num_replicas set to auto, SAM3 and cuRobo on a quarter GPU and PyRoki on two CPUs, and each episode as a Ray task on a quarter GPU](/blog_images/aspire-on-ray-code.png)

I work at Anyscale, which builds Ray. I haven't ported ASPIRE yet. Triton and Knative do parts of this too.

## What I'll measure next

ASPIRE logs each service's calls and seconds per episode. Time between calls over time per call is how many sims one copy feeds. That sets batch sizes and copy counts.
